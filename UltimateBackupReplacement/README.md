# Ultimate Backup Replacement - сборка и запуск

Код прошёл проверку реальным компилятором (mono mcs) против стаб-библиотеки,
повторяющей сигнатуры Rage API - это ловит опечатки, несовпадения типов и
пропущенные using'и, но **не гарантирует**, что каждый нативный вызов
(`NativeFunction.Natives.XXX`) и точное имя метода в реальном RPH SDK
совпадает 1:1 - у меня нет доступа к сайту RAGE Plugin Hook, чтобы скачать
настоящие DLL и собрать против них. Собрать и проверить в реальной VS с
реальным SDK нужно тебе.

## Что нужно скачать самому

1. **RAGE Plugin Hook** (https://ragepluginhook.net/, тебе нужен установщик +
   "Plugin API" из раздела Downloads). После установки в папке RPH будет
   `RAGEPluginHook.exe` - именно на него ставится референс как на assembly.
2. **RAGENativeUI** - используется для меню (Select Unit и т.п.). Возьми DLL
   из последнего релиза на GitHub (LMSTUDIOS/RAGENativeUI или актуальный форк,
   уточни у сообщества LSPDFR/RPH какой форк сейчас живой).
3. (опционально) **LSPDFR SDK**, если захочешь дергать `Functions.Arrest`,
   `Functions.RequestDriverLicense` и подобные готовые обёртки вместо ручных
   нативов - `LSPD First Response.dll` из установленного LSPDFR.

## Сборка

1. Открой `UltimateBackupReplacement.csproj` в Visual Studio (2019+, .NET
   Framework 4.8 таргет уже прописан).
2. Положи `RAGEPluginHook.exe` и `RAGENativeUI.dll` в папку `lib/` рядом с
   `.csproj` (пути уже прописаны в `<HintPath>`).
3. Если используешь LSPDFR SDK - добавь ещё один `<Reference>` на
   `LSPD First Response.dll` в `.csproj` по аналогии.
4. Build → Release, x64.
5. Готовый `UltimateBackupReplacement.dll` скопируй в папку
   `Grand Theft Auto V/plugins/` (или `plugins/Managed/` в зависимости от
   версии RPH - смотри доки RPH под свою версию).

## Интеграция с LSPDFR SDK и Stop The Ped

### LSPDFR (`Compatibility/LspdfrBridge.cs`)
Через reflection на загруженную сборку LSPDFR (без жёсткой зависимости на компиляции -
если LSPDFR не установлен, методы просто молча возвращают false вместо падения):

- `RequestDriverLicense` / `RequestVehicleRegistration` / `RequestPedId` / `Arrest` -
  вызывают настоящую логику LSPDFR вместо собственных заглушек, с фоллбеком на
  voice line, если LSPDFR не загружен.
- `SetCopAsBusy(ped, true)` - вызывается при спавне **любого** юнита (Partner в
  `PartnerSpawner`, Code2/Code3 в `SpawnDispatcher`) сразу при создании ped'а.
  Это критично: без этого LSPDFR может параллельно выдавать нашим управляемым
  юнитам свои задачи (например пытаться отправить их патрулировать через свою
  систему), и два мода будут дёргать Task одного и того же ped'а одновременно.
- `IsPedAPoliceOfficer` - используется в `TargetingHelper.IsValidSuspectTarget`,
  чтобы Arrest/Force Arrest/Search Ped не могли случайно схватить другого
  офицера, если он оказался ближайшим/aimed ped'ом рядом с настоящим подозреваемым.

### Stop The Ped (`Compatibility/StopThePedCompatibility.cs`)
Раньше этот класс был декоративным - существовал, но ни разу не вызывался из
реальной логики (это был баг, отдельно нигде не задокументированный как таковой).
Теперь `IsPedBeingHandled(ped)` реально проверяется в `TargetingHelper.IsValidSuspectTarget`,
которую вызывают:
- `ArrestDispatcher.Arrest` / `ForceArrest`
- `SearchDispatcher.SearchPed`
- UI: Stop Ped / Request ID / Request Driver License / Request Registration / Request Exit Vehicle

Если STP прямо сейчас ведёт traffic stop с этим ped'ом - наши команды тихо
отменяются, чтобы не было двойного управления одним ped'ом.

**Честно про надёжность детекта STP**: у STP нет документированной публичной API,
поэтому `StopThePedCompatibility` перебирает несколько вероятных имён метода
(`IsPedBeingStopped`, `IsPedStopped`, `IsBeingStopped`, `IsPedHandled`, `IsPedBusy`)
и статических, и инстансных (`Main.Instance`). Если у твоей версии STP метод
называется иначе - открой её DLL в ILSpy/dnSpy, найди реальное имя и добавь
в массив `MethodNameCandidates`. Пока ни один кандидат не подойдёт, детект
просто не сработает (возвращает false), но это не ломает остальной функционал -
просто не будет защиты от двойного управления, пока не подставишь верное имя.

### Про хард-зависимость vs reflection
Оба моста сделаны через reflection, а не прямой референс на `.dll`, специально -
это значит плагин **соберётся и заработает**, даже если у пользователя не
установлен LSPDFR или STP (хотя без LSPDFR сам смысл мода теряется, раз это
LSPDFR-плагин). Если предпочитаешь жёсткую зависимость (что тоже нормальная
практика для RPH-плагинов) - добавь `<Reference>` на `LSPD First Response.dll`
в `.csproj` и замени вызовы в `LspdfrBridge` на прямые
`LSPD_First_Response.Mod.API.Functions.XXX(...)` - будет быстрее и ошибки
всплывут на компиляции, а не в рантайме.

## UI планшета (WPF)

Реализован как настоящее WPF-окно (`UI/Views/TabletWindow.xaml`), а не Scaleform -
RPH позволяет плагинам открывать полноценные Windows-окна поверх игры, что даёт
нормальную стилизацию (тёмно-синий LSPD-фон, толстая тёмная рамка "корпуса
планшета", три вкладки Partners/Code 2/Code 3).

**Важная техническая деталь**: WPF требует STA-поток, а RPH выполняет плагин не
на STA - поэтому окно живёт на отдельном выделенном потоке (`UI/TabletHost.cs`),
и любое обращение к нему из игрового потока идёт через `Dispatcher.BeginInvoke`.
Это правильный и стандартный подход для WPF-оверлеев в RPH-плагинах, ничего
переделывать не нужно, просто имей это в виду, если будешь добавлять что-то ещё
в окно - трогать элементы окна можно только из его собственного Dispatcher.

**Честно об ограничении проверки**: весь C#-код в `Core/`, `Units/`, `Commands/`,
`Input/`, `UI/TabletUI.cs`, `UI/TabletHost.cs` я прогнал через настоящий
компилятор (mono mcs) против стаб-библиотеки, повторяющей Rage API - там 0 ошибок.
`UI/Views/TabletWindow.xaml` и `TabletWindow.xaml.cs` собрать в этом контейнере
**нельзя** - WPF (`PresentationFramework`/`PresentationCore`) существует только
под Windows, в Linux-контейнере таких сборок физически нет. Этот файл написан
по знанию WPF API, но не прогнан через компилятор - при первой сборке в Visual
Studio почти наверняка вылезут мелкие ошибки (опечатка в имени свойства,
не тот тип аргумента и т.п.) - это нормально для WPF-кода такого объёма без
живой сборки, просто занимает 10-15 минут на правку по сообщениям компилятора.

- Вкладки Partners / Code 2 / Code 3 с переключением
- Список юнитов (multi-select), Select All для Partners

### Changelog: найденные и исправленные баги (ревизия после первичной сборки)

- **Спам команд при удержании клавиши.** B/O/T проверялись через `IsKeyDownRightNow`
  без edge-detection - пока клавиша была зажата, Force Arrest/Get In Vehicle
  запускались заново каждый кадр (60 раз/сек). Добавлено сравнение с состоянием
  предыдущего кадра (`_prevB/_prevT/_prevO`), команды теперь срабатывают один раз
  на нажатие.
- **Covering-юниты застревали навечно.** После Force Arrest/Search Ped юниты в
  роли covering/guard держали прицел бесконечно, даже когда primary уже закончил
  и suspect был закован. Теперь они следят за `primary.State` и возвращаются в
  Idle сразу после завершения.
- **Детект "по нам стреляют" не работал.** `GET_PED_SOURCE_OF_DEATH` реагирует
  только на смерть ped'а, не на входящий урон - для живого юнита auto-cover
  никогда бы не сработал. Заменено на отслеживание падения `Health` между
  проверками + поиск ближайшего реально стреляющего ped'а (`IS_PED_SHOOTING`)
  в радиусе как источника угрозы.
- **Неверный натив для road node.** `GET_CLOSEST_VEHICLE_NODE` не возвращает
  heading - нужен `GET_CLOSEST_VEHICLE_NODE_WITH_HEADING`.
- **Race condition в детекте побега при Force Arrest.** Flee-таск запускается
  в момент вызова команды, а проверка `IsFleeing` шла один раз почти сразу же -
  suspect мог физически не успеть тронуться с места, и primary шёл на мирный
  takedown вместо предупреждений. Заменено на поллинг каждые 300мс в течение
  до 3 сек, пока идёт сближение.

## Оптимизация

Раньше вся боевая AI-логика по юнитам (`CheckUnderFire`/`UpdateCoverBehavior`/
`WatchdogTick`) и очистка мёртвых юнитов гонялись **каждый кадр** (60 раз/сек)
для каждого активного юнита - при 8+ NOOSE, 8+ SWAT и партнёрах разом это
реально нагружает CPU без всякой пользы (реакция "укрылся за 200мс вместо 16мс"
неотличима на глаз).

Теперь `Main.cs` держит два независимых цикла:
- **FastLoop** (каждый кадр) - только `KeyBindings.Tick()`, нужен per-frame
  ради точного hold-vs-tap на U и edge-detection на B/O/T.
- **SlowLoop** (раз в 200мс) - вся AI-логика по юнитам + `PurgeDead()`.

Важно: таймеры (`StuckTimer`, `TimeInVehicleCover`) раньше инкрементировались
через `Game.FrameTime` (дельта одного кадра ~16мс) - при переносе в SlowLoop
это занижало бы накопление в ~12 раз (10-секундный релокейт укрытия растянулся
бы почти на 2 минуты). Заменено на константу шага SlowLoop (0.2 сек).

## Визуал

- Список юнитов теперь показывает цветной индикатор статуса (зелёный - Idle,
  синий - в движении/задаче, янтарный - выполняет команду типа ареста/обыска/
  лечения, красный - под огнём/в бою) вместо голого текста.
- Кастомный `ListBoxItem` стиль - подсветка выделения и hover в тон общей
  тёмно-синей темы вместо системного синего WPF-выделения.
- На кнопках вкладок теперь счётчик юнитов: "PARTNERS (3)", "CODE 2 (5)".
- В шапке добавлены живые часы (обновляются раз в секунду через DispatcherTimer).
- `TabletHost.Shutdown()` + хук на `AppDomain.ProcessExit` - WPF-поток корректно
  закрывается при выгрузке плагина, а не остаётся висеть в фоне (актуально при
  hot-reload плагина в RPH во время разработки).
